# 智扫通 Agent 企业级优化蓝图

> 本目录只保存分析与实施设计，不修改、不复制现有 Demo 的业务代码、知识库和配置。当前版本是规划基线，不是可运行的新系统。

## 1. 结论先行

现有项目已经完成了一个垂直领域 Agent 的关键技术闭环：Streamlit 对话入口、LangChain Agent、工具调用、中间件、Chroma 检索增强生成（RAG）以及使用报告场景切换。它适合作为功能验证 Demo，但距离可对客户稳定交付的企业级产品仍有明显差距。

当前成熟度可判断为 **PoC / Demo（约 30%）**，而不是生产 MVP。主要原因不是 Agent 主链路缺失，而是用户身份、真实数据、可靠性、安全、评测、运维和交付体系尚未建立。

### 当前已完成

- 可通过聊天界面发起问题并流式展示回答。
- 已接入通义聊天模型和向量模型。
- 已定义知识问答、天气、用户、月份、外部记录和报告上下文等工具。
- 已具备本地知识文件加载、切分、向量化、检索和总结链路。
- 已用中间件记录工具调用，并按上下文切换报告提示词。
- 已准备扫地机器人知识资料和模拟用户月度数据。

### 生产化缺口概览

| 维度 | 现状 | 用户影响 | 目标状态 | 优先级 |
|---|---|---|---|---|
| 产品体验 | 单页聊天 Demo | 无登录、无会话恢复、无反馈、失败不可理解 | 登录后可连续服务、可追踪、可反馈 | P0 |
| 数据真实性 | 用户、月份、位置随机；天气固定；CSV 模拟 | 同一问题结果漂移，个人报告不可信 | 绑定真实用户与受控业务数据源 | P0 |
| 安全合规 | 模型密钥明文保存在配置中 | 存在密钥泄露和费用滥用风险 | 立即轮换，使用环境变量或密钥管理 | P0 |
| Agent 可靠性 | 流程主要由提示词约束 | 关键报告步骤可能漏调、乱序或重复 | 报告采用确定性工作流和可恢复状态 | P0 |
| 服务架构 | UI 直接创建 Agent 和依赖 | 难扩容、难复用、难隔离故障 | 前后端/API/领域服务/基础设施分层 | P0 |
| RAG 质量 | 固定 Top-K、MD5 增量、本地 Chroma | 无引用、难更新删除、命中质量未知 | 可追溯索引、混合检索、重排和评测 | P1 |
| 质量保障 | 无自动测试、评测集和质量门禁 | 修改后容易静默退化 | 单测、集成、端到端与 Agent 评测 | P0 |
| 可观测性 | 本地文本日志 | 无请求链路、指标、成本和告警 | 结构化日志、Trace、指标、审计 | P1 |
| 工程交付 | 无依赖锁定、容器、CI/CD 和文档 | 环境不可复现，无法稳定发布 | 可复现构建、分环境配置、灰度回滚 | P0 |
| 治理运营 | 无管理后台与知识审批 | 内容更新依赖开发者手工操作 | 知识版本、审批、发布和效果看板 | P2 |

## 2. 用户视角的产品目标

企业化不能只把代码拆成更多目录。建议先以四类用户定义成功标准：

1. **终端用户**：能快速得到可信答案；不知道怎么问时有引导；回答给出来源；失败时知道下一步；个人报告必须属于本人。
2. **客服/运营人员**：能看到低满意度会话、人工接管、纠错知识并验证效果，而不是只能查看开发日志。
3. **知识管理员**：能上传、校验、审批、发布、撤回和追踪知识版本，删除文档后索引同步删除。
4. **平台管理员**：能控制租户、账号、权限、模型配额、敏感操作与审计记录。

建议首个生产 MVP 聚焦三条旅程：

- **故障排查**：用户描述现象 → Agent 补问关键条件 → 检索可信步骤 → 给出逐步处理和安全边界 → 未解决时转人工。
- **知识咨询**：用户咨询选购/维护 → 给出简明结论和来源 → 支持追问 → 收集有用/无用反馈。
- **个人报告**：完成身份校验 → 选择月份 → 获取本人数据 → 生成结构化报告 → 支持导出或分享（是否实现需确认）。

生产 MVP 建议指标：首字响应时间、完整响应 P95、任务完成率、引用命中率、无依据回答率、报告数据一致率、转人工率、用户满意度、单次会话成本。

## 3. 关键技术差距

### 3.1 产品与前端

- 对话仅保存在 Streamlit Session，刷新或换设备后丢失。
- Agent 每个会话独立初始化，模型、向量库等重资源生命周期不可控。
- 没有身份认证、会话列表、停止生成、重试、反馈、引用展示、文件入口和人工兜底。
- 流式结果只保存最后一个 chunk 的逻辑存在丢失完整回答的风险；角色字符串也存在拼写错误。
- 当前代码未将历史消息传回 Agent，多轮界面看似存在，但模型实际上每次只收到本次输入。

### 3.2 Agent 与业务流程

- 报告流程依赖提示词要求模型按固定顺序调用工具，缺少代码层状态机、参数校验和幂等保障。
- 报告上下文是一次请求内的可变字典，没有稳定、可持久化的会话状态模型。
- 工具没有统一超时、重试、熔断、权限、错误码和降级契约。
- 工具返回类型与声明不完全一致，例如外部数据工具标注返回字符串，实际可能返回字典。
- 没有输入注入防护、输出安全策略、敏感数据脱敏和高风险操作确认。
- 提示词要求暴露“真实思考过程”，这不适合作为生产产品行为；应改为简短进度说明和可审计决策摘要。

### 3.3 数据与 RAG

- 知识索引依靠 MD5 文本文件判断新增，无法可靠处理更新、删除、失败回滚和并发导入。
- 文档元数据、版本、权限、租户隔离、来源 URL、发布日期和有效期没有标准模型。
- 检索只有向量 Top-K，没有关键词/混合检索、过滤、重排、查询改写和置信度门槛。
- 回答没有可展示引用，用户无法验证信息来源。
- 索引构建与在线查询共用应用工程，没有离线任务、状态追踪和失败重试。
- RAG 链会直接打印完整提示词和资料，可能将用户问题或知识内容泄露到控制台日志。

### 3.4 安全与隐私

- 配置文件包含可用形式的明文 API Key；应视为已经泄露并立即轮换。
- 随机用户 ID 直接用于查询个人记录，不具备身份绑定和数据授权。
- 没有权限模型、租户隔离、审计日志、数据保留/删除策略、传输与存储加密约束。
- 本地日志可能记录工具参数、用户问题和返回内容，没有脱敏与访问控制。
- `.gitignore` 为空，日志、向量库、密钥和本地数据容易被误提交。

### 3.5 工程质量与交付

- README 为空，缺少安装、运行、配置、架构和排障说明。
- 没有依赖声明和锁文件，无法复现运行环境，也无法进行依赖安全扫描。
- 没有单元、集成、端到端测试，也没有离线 Agent/RAG 评测集。
- 没有 API 契约、数据库迁移、任务队列、缓存和服务健康检查。
- 没有容器、CI/CD、开发/测试/生产环境隔离、版本策略和回滚方案。
- 日志以进程本地文件保存，没有 request_id、conversation_id、tool_call_id、延迟、Token、成本和告警指标。
- 当前根目录没有可用的 Git 工作树信息；正式优化项目需要独立版本库或确认上层仓库策略。

| 编号 | 冲突点 | 当前设计 | 建议 | 需要你确认什么 |

| C01 | 思考过程展示 | 提示词要求输出真实思考过程 | 只展示“正在查询知识库”等进度与简短依据，不展示内部推理 | 是否接受调整用户可见内容 |
| C02 | 报告编排 | 由模型自行决定固定工具顺序 | 改为代码控制的确定性工作流，Agent 只负责理解与生成 | 是否接受降低该场景的 Agent 自主性 |

| C10 | 原数据迁移 | Demo 已有 Chroma/MD5 数据 | 新项目重新构建可追踪索引，默认不复制旧索引 | 是否需要迁移旧知识和历史数据 |

安全处置不建议等待架构决策：请立即在供应商侧吊销并轮换现有密钥。为了遵守“不修改原内容”的要求，蓝图不会替你删除原配置；轮换后应避免继续运行旧 Demo，或由你另行授权进行安全清理。

## 5. 目标架构

建议采用“模块化单体 + 异步任务”的第一阶段架构，先确保边界清晰、可测试、可部署，再根据实际负载拆微服务，避免为 Demo 过早引入分布式复杂度。

```text
正式 Web / 内部调试台
        |
API 网关：认证、限流、请求 ID、流式协议
        |
应用层：会话服务 / 问答用例 / 报告工作流 / 反馈服务
        |
领域层：Agent 编排 / 工具契约 / RAG / 安全策略
        |
适配器：模型网关 / 用户系统 / 业务数据 / 天气 / 向量检索
        |
基础设施：PostgreSQL / Redis / 向量库 / 对象存储 / 任务队列
        |
治理：日志、Trace、指标、评测、审计、CI/CD、告警
```

推荐新项目目录（C04/C05 等确认后再创建实现代码）：

```text
enterprise_agent/
  apps/api/                 # 对外 API 与流式协议
  apps/web/                 # 正式 Web（若批准）
  apps/admin/               # 知识与运营后台（后续）
  src/application/          # 用例与工作流
  src/domain/               # 领域模型和接口
  src/infrastructure/       # DB、模型、向量库、外部服务适配器
  src/observability/        # 日志、追踪、指标
  workers/                  # 知识导入、评测等异步任务
  evals/                    # 黄金问题集和回归阈值
  tests/                    # 单元、契约、集成、端到端测试
  deploy/                   # 容器与环境部署文件
  docs/                     # ADR、API、运维和用户说明
```

## 6. 分工作区执行方案

每个工作区都在根目录下使用独立的新目录或独立 Git worktree，绝不覆盖原 Demo。推荐先建立一个只含契约的 `enterprise_agent` 主干，再让各工作区按下表工作；合并顺序由依赖关系决定，而不是同时堆功能。

### 工作区 WS-0：决策与安全基线（低复杂度，1–2 天）

**目标**：关闭方向性风险，让后续团队不在错误假设上开发。

执行步骤：

1. 逐项确认 C01–C10，记录架构决策 ADR。
2. 在供应商侧轮换泄露密钥，并确定密钥管理方式。
3. 明确首期用户、三条核心旅程、SLO、预算和验收指标。
4. 确定数据分级、日志脱敏、保留周期与人工兜底责任人。

交付物：决策记录、产品范围、威胁模型、验收指标。门禁：P0 决策无悬而未决项。

### 工作区 WS-1：工程骨架与开发体验（低复杂度，2–4 天）

**目标**：创建可重复构建、可测试的新项目空骨架。

执行步骤：

1. 在 `enterprise_agent/` 建立模块化目录，不复制旧密钥、日志和向量库。
2. 固定 Python 版本和依赖锁，增加环境变量模板与配置校验。
3. 配置格式化、静态检查、类型检查、提交检查和基础测试框架。
4. 建立容器、健康检查、本地开发编排和 CI 质量门禁。
5. 编写快速开始、配置说明、架构图和故障排查文档。

交付物：空服务可启动、健康检查通过、CI 通过。依赖：WS-0。

### 工作区 WS-2：核心服务与真实身份（中复杂度，5–8 天）

**目标**：把“聊天脚本”变成有清晰契约的可复用服务。

执行步骤：

1. 定义用户、租户、会话、消息、反馈和报告的数据模型。
2. 建立 API 与流式事件协议，支持取消、超时、重试和标准错误码。
3. 接入认证与权限，用户 ID 只能来自可信登录态。
4. 持久化会话和完整消息，正确向 Agent 提供受控历史上下文。
5. 建立模型网关、超时/重试/限额和开发 Mock 适配器。

交付物：已认证用户可跨刷新继续会话；越权测试通过。依赖：WS-1、C03/C06/C07。

### 工作区 WS-3：Agent 与工具可靠性（中高复杂度，6–10 天）

**目标**：让关键任务可预测、可恢复、可审计。

执行步骤：

1. 为每个工具建立强类型输入输出、错误码、超时、重试和幂等规则。
2. 将个人报告改为显式状态机：鉴权 → 选择月份 → 取数 → 校验 → 生成。
3. 普通知识问答保留 Agent 路由，但增加最大步数、预算和失败降级。
4. 增加提示注入防护、工具权限校验、敏感输出过滤和人工转接策略。
5. 提示词版本化，并让每次请求记录版本、模型与工具轨迹。

交付物：报告流程顺序与数据一致性自动验证；工具故障可降级。依赖：WS-2、C01/C02/C09。

### 工作区 WS-4：知识与 RAG 平台（高复杂度，8–12 天）

**目标**：让回答可追溯、知识可运营、质量可度量。

执行步骤：

1. 定义文档、版本、分片、权限、来源和索引任务模型。
2. 建立离线导入流水线，支持校验、去重、更新、删除、失败回滚。
3. 实现混合检索、元数据过滤、重排、置信度阈值和无答案策略。
4. 返回可展示引用，并在用户界面提供来源片段。
5. 用现有资料构建脱敏基准集，调优切分、Top-K 和重排参数。

交付物：知识增删改可追踪；回答引用可核验；RAG 指标达到门槛。依赖：WS-1，可与 WS-2/3 部分并行；C05/C07/C10。

### 工作区 WS-5：用户体验与运营闭环（中高复杂度，6–10 天）

**目标**：把技术能力变成用户愿意持续使用的产品。

执行步骤：

1. 按三条核心旅程设计首页引导、澄清提问和结构化结果。
2. 增加会话历史、停止生成、重试、复制、引用和反馈。
3. 对超时、无答案、数据缺失、权限不足提供可行动的提示。
4. 增加人工接管入口与运营反馈闭环。
5. 进行真实用户可用性测试和无障碍/移动端检查。

交付物：核心旅程端到端可用，用户测试问题闭环。依赖：WS-2/3/4、C04/C08。

### 工作区 WS-6：质量、可观测与安全（高复杂度，贯穿实施，8–12 天）

**目标**：上线前能证明系统可靠，而不是只证明“能跑”。

执行步骤：

1. 建立单元、契约、集成、端到端及故障注入测试。
2. 建立知识问答、工具选择、报告一致性、安全对抗评测集。
3. 增加结构化日志、分布式 Trace、延迟/Token/成本/错误指标。
4. 配置 SLO、仪表盘、告警、审计查询和隐私脱敏检查。
5. 执行依赖扫描、密钥扫描、权限测试、压测与恢复演练。

交付物：质量报告、上线门禁、告警手册、审计记录。依赖：从 WS-1 开始并行，最终覆盖 WS-2 至 WS-5。

### 工作区 WS-7：部署、灰度与运营（中高复杂度，5–8 天）

**目标**：安全上线并具备回滚、扩容和持续运营能力。

执行步骤：

1. 建立开发、测试、预发布、生产环境及数据库迁移流程。
2. 配置镜像发布、配置注入、备份恢复、滚动/蓝绿部署。
3. 先内部试用，再按用户比例灰度，设置自动停止条件。
4. 验证容量、成本、限流、降级和回滚流程。
5. 移交用户手册、运营手册、值班手册和版本发布节奏。

交付物：预发布验收、灰度报告、回滚演练和生产发布清单。依赖：WS-2 至 WS-6。

## 7. 推荐节奏与并行关系

```text
WS-0 决策与安全
  └─ WS-1 工程骨架
       ├─ WS-2 核心服务与身份 ─┬─ WS-3 Agent可靠性 ─┐
       ├─ WS-4 RAG平台 ─────────┤                  ├─ WS-5 用户体验
       └─ WS-6 质量与观测（持续覆盖所有工作区）──────┘
                                                    └─ WS-7 灰度上线
```

单人实施建议按 WS-0 → 1 → 2 → 3 → 4 → 5 → 6 → 7；多人实施时，WS-2 与 WS-4 可并行，WS-6 从第一天伴随开发。以 2–3 名工程人员估算，生产 MVP 通常为 6–10 周；多租户管理后台、复杂运营和多模型容灾应作为后续版本，而不是首期阻塞项。

## 8. 分阶段验收门槛

### M1：可重复开发

- 新成员按文档在限定时间内启动服务。
- 代码、配置、依赖和数据库结构可复现。
- 仓库无密钥、日志、个人数据和生成索引。

### M2：可安全试用

- 登录、权限、会话持久化和报告数据归属通过测试。
- 故障排查、知识咨询、个人报告三条旅程可端到端完成。
- 模型/工具故障有明确降级，不向用户暴露堆栈或内部推理。

### M3：可灰度上线

- 离线评测、对抗评测、压测和恢复演练达到既定阈值。
- 关键指标、告警、审计、成本与回滚全部可用。
- 运营和支持人员已具备知识更新、反馈处理和人工接管能力。
